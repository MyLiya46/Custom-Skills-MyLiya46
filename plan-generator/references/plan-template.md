# Plan 文件模板与命名规范

计划文件默认存放于 docs/plans/，一任务一文件，互不重名。

## 命名规范

T{n}-description-of-the-plan-YYYY-MM-DD.md

## 字段结构

计划文件保存执行详情，不保存生命周期状态；生命周期状态统一写在 docs/todo.json，todo.md 只是生成视图。

示例结构：

    # T{n} · 标题（英文短名）

    - 任务 ID：T{n}
    - 标题与目标：（一句话说明可验证交付物）
    - 关联文档章节：（PRD / 技术设计章节）
    - 前置依赖 blockedBy：（无 | T{n}、T{n}，与 todo 严格一致）

## 执行画像（可选，供 plan-executor 设置运行窗口）

    - execution_mode：（worker | direct；默认 worker，恢复时不得切换）
    - execution_class：（short | normal | long-infra | external | e2e）
    - expected_duration：（约时长或历史 P95；未知时写“按验收命令推断”）
    - external_waits：（无 | PG / 服务启动 / HTTP 任务 / LLM / 其它）
    - checkpoint_phases：（阶段名，逗号分隔）
    - resume_boundary：（失败后从哪个阶段或验收项继续）

    ## 问题
    - 背景与当前问题：（可验证的问题描述）

    ## 决策
    - 目标方案：（明确选择与关键参数）

    ## 范围
    - 包含：（任务边界与涉及文件）
    - 不包含：（明确排除项）

    ## 环境预检
    - 必需 Shell：（pwsh | git-bash | 其它）
    - 必需命令：（python、uv、npm、docker、psql 等）
    - 必需端口：（8000、8001 等；无则写无）
    - 必需 URL：（健康检查地址；无则写无）
    - 必需 Python 模块：（psycopg2 等；无则写无）
    - 必需 Docker 容器：（容器名；无则写无）
    - 容器内必需命令：（容器名:命令，如 pg:psql；无则写无）
    - 容器内必需 Python 模块：（容器名:模块名；无则写无）
    - 执行画像：（short | normal | long-infra | external | e2e）
    - 启动超时（秒）：（首次 ACK/启动窗口）
    - 空闲超时（秒）：（无进度证据的观察窗口）
    - 硬截止（秒）：（整个任务绝对截止时间）
    - 最大 checkpoint 间隔（秒）：（每个实施阶段不得超过此间隔；按阶段单独写在步骤参数中）
    - 预检命令：
      ```bash
      python <skill_root>/scripts/preflight.py check --plan <plan-path> --format json
      ```

    ## 风险与回滚
    - 风险：（触发条件、影响和监测方式）
    - 回滚：（可执行的恢复命令或反向操作）

    ## 实施步骤

    ### 步骤 1：（步骤标题）
    - 对象：（具体模块、文件、接口或数据）
    - 动作：（创建、修改、迁移、删除或验证）
    - 参数：（具体参数值、输入输出或边界）
    - 核心修改文件：（相对路径，允许直接修改）
    - 必要集成文件：（相对路径，允许为挂载路由、注册入口或配置接线修改）
    - 命令：
      ```bash
      （可直接运行的实施或验证命令）
      ```

    ## 完成标准
    - 验收类型：（offline | external | mixed）
    - 离线验收命令：
      ```bash
      （可直接运行的验收命令）
      ```
    - 外部环境验收命令：（offline 类型写无，否则写健康检查、curl、E2E 或轮询命令）
    - 通过条件：（退出码、断言或可观察结果）

## 写作规则

- 每条步骤必须落到“对象 + 动作 + 参数值”。
- 涉及文件直接写在步骤中；只有需要给 executor 明确白名单时才额外列出文件清单，避免重复复制路径。
- 跨任务共享的口径直接保留在 todo.json 的关键口径字段，不新增独立决策文件；todo.md 由脚本导出。
- 可保留具体的【假设：...】，但不得把“占位、待定、待确认”当作参数值。
- 验收标准必须能直接运行或由明确命令验证，禁止只写“功能可用”“体验良好”。
- plan 评审通过后只更新 docs/todo.json 的状态；旧 plan 中已有的“状态”字段不主动删除或重写。
- 执行画像描述运行窗口和恢复边界，不是生命周期状态；不得把 `pending`、`reviewed`、`in_progress` 等状态写入 plan 作为调度真值。
- 执行画像缺失时 executor 必须兼容旧 plan，并按验收命令中的 PG、服务启动、外部 HTTP 或 E2E 依赖保守推断，不因缺字段使用激进短超时。
- 必备二级章节及顺序固定为：问题 → 决策 → 范围 → 环境预检 → 风险与回滚 → 实施步骤 → 完成标准；缺失、重复或乱序均不能评审通过。
- 每个实施步骤必须有对象、动作、参数、核心修改文件、必要集成文件和可直接运行的命令；完成标准必须区分离线验收与外部环境验收。
- 核心修改文件是实现主体，必要集成文件是挂载路由、注册入口、配置接线等允许触碰的边界；两者必须显式列出，禁止让 worker 自行猜测入口。
- 新计划必须声明 Shell、命令、端口、URL、Python 模块、容器和最大 checkpoint 间隔；旧计划可以按兼容规则执行，但续写或修改时应迁移到新字段。
- 风险必须同时写出触发条件与影响，回滚必须是可执行的反向操作或命令；禁止使用 `TBD`、`TODO` 或空字段逃避决策。
