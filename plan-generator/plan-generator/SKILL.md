# task-planner · 方案拆解 + 逐条计划评审

## 何时使用

当用户投喂一份 PRD / 方案报告 / 技术方案（或类似文档），并期望得到：

1. **Plans**：一任务一计划文件，任务间用前置依赖（blockedBy）连接；
2. **Todos**：一张拓扑有序的任务清单；
3. **逐条评审**：对本次新增的每份计划与用户一对一过一遍，消灭「待定 / 占位 / 等用户补 / 冲突未解」等未尽事项。

核心诉求是**可执行粒度**：每个任务的实施步骤必须细化到具体操作与明确参数——落到「对象 + 动作 + 参数值」，并附可运行验收项；禁止残留「待定 / 占位 / 待确认」等未决条目，确保任一计划拿到手即可无歧义开工。

## 目标（优先级 1 > 2 > 3）

1. **拆解**：把源方案全量拆成一组 Plans + 一张 Todos；
2. **评审**：逐个与用户评审本次新增的每份计划，推进到「零占位、零冲突、零模糊」，单条不设轮次上限；
3. **同步**：每份计划通过后，把对应任务在 Todos 中的状态由 `pending` 更新为 `reviewed`。

## 任务状态（Status）

`Todos` 列表「状态」列与计划文件「状态」：

| 状态值 | 语义 | 由谁设置 |
|---|---|---|
| `pending` | 待评审（任务拆解后的初始态） | 拆解阶段默认赋 |
| `reviewed` | 已评审，可开工 | 阶段二逐条评审通过后 |
| `completed` | 已完成 | 用户交付验收后自置 |
| `blocked` | 阻塞（前置依赖未完成、或存在未决假设暂缓） | 用户或异常兜底 |

状态流转：`pending → reviewed → completed`；`blocked` 为旁路态，可随时标记，解除后回到 `reviewed`。skill 只负责写入 `pending`（拆解产物）与 `reviewed`（评审通过）两个状态；`completed` / `blocked` 由用户在使用过程中自行维护。

## 使用模式：首次 / 续写 / 覆盖重拆

| 模式 | 触发条件 | 行为 |
|---|---|---|
| 首次 | 当前目录无 `docs/plans/`、无 `docs/todo.md` | 从零新建，任务 ID 从 T01 起 |
| 续写（默认） | 已有 `docs/plans/` 与 `docs/todo.md` | 见下方「续写规则」 |
| 覆盖重拆 | 新方案要替换既有任务口径 | 先向用户确认范围，再执行 |

### 续写规则（第二次使用）

- **保留不动**：既有计划文件、任务行、拓扑注释一律不删不改。
- **ID 递增**：新任务接在现有最大号之后（如已有 T73，从 T74 起），禁止重号。
- **日期当天**：新计划文件沿用 `T{n}-description-YYYY-MM-DD.md`，日期取本次当天，可与旧任务不同日。
- **blockedBy 可跨代引用**：新任务可依赖既有任务（含 completed）作前置，照实填入；拓扑注释只新增本次说明，不重写历史条目。
- **交付物核对**：只核本次新增项，历史条目原样。
- 若本次新需求必须改动旧任务 / 旧计划文件：先列冲突点向用户确认，再动，不得静默改写。

## 输入

- **主输入**：源方案文档，通常为 `docs/PRD.md`（也可为方案报告、技术方案等，唯一需求口径）。
- **可选输入**：已有 `docs/plans/` + `docs/todo.md`——第二次使用时用于**续写**（识别既有任务 ID、依赖与约定），见「使用模式」。
- **模板**：计划文件命名规范与字段结构见 [references/plan-template.md](references/plan-template.md)；任务清单三段结构与表格字段见 [references/todo-template.md](references/todo-template.md)。**默认严格遵循模板，除非用户另行指定其它项目约定。**

## 工作流程

### 阶段一 · 拆解

0. **识别模式**：按「使用模式」判定首次 / 续写 / 覆盖重拆；续写时先读既有 `docs/todo.md` 与 `docs/plans/`，确认现有最大任务 ID 与约定。
1. **通读源方案**：梳理全部 capability / 入口 / 分派逻辑 / 改造线，列清单。
2. **识别依赖**：在能力内部与能力之间标注 blockedBy，保证拓扑为单向无环 DAG；可并发任务明确写出。
3. **确定任务边界**：以「单一事实来源」「零回归」为切分原则；边界决策落为任务内硬约束。
4. **写计划文件**：逐任务按 [references/plan-template.md](references/plan-template.md) 补齐字段，落笔即消灭占位。
5. **写任务清单**：按 [references/todo-template.md](references/todo-template.md) 以拓扑顺序写入或续写，附拓扑注释与交付物核对；续写模式下只追加新任务行与拓扑说明，不重排既有条目。

### 阶段二 · 逐条评审（一对一）

6. **自检**：对每份新增计划先跑「禁止占位词」与「细致度正反例」（见下），自查不达标处自行补位；无法定的列成「待确认疑点」。
7. **逐条评审**：按拓扑顺序，**一次只处理一份计划**：
   - 展示该计划摘要 + 疑点清单；
   - 请用户确认或指出问题（不批量跳号）；
   - 通过 → 进入下一份；
   - 指出问题 → 当场修订该计划文件并就地重审，直到通过（单条不限轮次）。
8. **同步状态**：每份计划通过后，把对应任务在 Todos 中「状态」标为「已评审 / 可开工」。

## 质量判定线（评审即返工的边界）

**每条实施步骤必须落到「对象 + 动作 + 参数值」；禁止占位/待定字眼。**

反例（见即返工）：
- ❌ 「调用 XX 服务获取数据」——缺接口、缺入参
- ❌ 「优化查询性能」「做一下错误处理」——无对象、无量化
- ❌ 「后续由用户排版」「有待解决冲突」「TBD / TODO / 占位 / 待定 / 待确认 / 待拍板」——占位词直接否决
- ❌ 「视情况调整参数」——无取值
- ❌ 验收项是「功能可用」这类无法跑命令验证的口号

正例（可直接开工）：
- ✅ 步骤落到「对象 + 动作 + 参数」：如「在 `run_flow` 中将 `MAX_AGENT_ROUNDS` 设为 `10`」
- ✅ 验收项是可执行命令：`pytest tests/test_engine.py -k send` 通过 / `curl -s localhost:8000/healthz` 返回 200
- ✅ 参数无法确定：不写占位，改为「列疑点向用户确认」，确认后再落数

## 约束条件
- 拆解只产出计划与清单文档，不修改任何源码。
- 源方案标【假设】的项保留标记，不擅自当已决事实；「待外部/后续」项拆为条件或后续项，不作当前阻塞。
- 未显式覆盖时，遵循 [references/](references/) 中的默认模板与命名约定。

## 边界与异常处理
- 源方案与技术基线冲突 → 以技术基线为准，在对应计划里点明冲突与取舍。
- 依赖未写明 → 按最小无环原则取最小合理依赖，显式标【假设】。
- 某步参数无法确定 → 不写占位，列入「待确认疑点」，评审时提问。
- 单条计划反复无法通过 → 不擅自定界，未决项标【假设】并记录，继续其它计划，最后汇总裁决。

## 禁止事项
- 不要在计划文件里残留「待定 / TBD / 等用户 XX / 有待解决 / 占位 / 后续再定」等字眼。
- 不要批量跳号评审，或未获用户通过就标「已评审」。
- 不要自造表名、事件名、错误码、工具名（严格对照源方案 / 技术基线）。
- 不要写无法验证的模糊验收项（「优化」「完善体验」）。
- 不要默认能猜到用户未写清的边界——要么依据源方案，要么显式标【假设】或提问。

## 验收标准
- [ ] 源方案全部能力/入口/改造线都有对应任务，无遗漏，拓扑为无环 DAG。
- [ ] 每个新增计划含 blockedBy / 实施要点 / 涉及文件 / ≥1 条可运行验收项，文件名符合模板且互不重名。
- [ ] 本次新增的每一份计划均已逐个与用户评审通过，无占位/待定字眼。
- [ ] 通过计划的对应任务在 Todos 中已标「已评审 / 可开工」，清单与 blockedBy、拓扑注释一致。
- [ ] 每条步骤落到「对象+动作+参数值」，验收项均可直接跑命令验证。

## 交互约定
- 执行前如发现影响任务边界的歧义，先列疑点确认，不擅自定界。
- 评审阶段一对一逐条推进；输出后欢迎增删改，本轮最多迭代 3 轮。
