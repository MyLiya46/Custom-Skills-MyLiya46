# 原子化提交（Atomic Commits）最佳实践

## 什么是原子化提交

每个 commit 只做**一件**逻辑上独立的事。它是可独立回滚、独立评审、独立被 `git revert` 的最小单元。

> 判断标准：如果这条 commit 需要两句话才能解释清楚，那它很可能不是原子的，应该拆成两条。

## 为什么

- **可回滚**：撤销某个改动不会连带丢掉无关改动。
- **可追溯**：`git blame` / `git bisect` 定位问题时，能精确到「哪次提交引入了它」。
- **可评审**：评审者一次只理解一个意图。
- **历史干净**：读者能顺着 commit 顺序读懂项目的演进，而不是面对一大坨「mixed changes」。

## 拆分原则

1. **按逻辑主题，不按文件**。一个 feat、一个 fix、一个 docs 各自独立成 commit。
2. **feat 与 fix 与 docs 绝不混入同一 commit**：新增功能、修 bug、改文档是三类不同意图。
3. **每组内文件服务于同一主题**：例如「新增一个模型接口」的 commit 可以同时包含后端接口 + 对应 schema，因为它们共同构成一个完整功能。
4. **untracked 新文件谨慎处置**：默认不纳入，单独列出并询问，避免把「随手新建的临时文件」误提交进功能 commit。
5. **同一文件多个逻辑改动**：默认按整文件归组；若一个文件里同时混了「新增功能」和「修另一个 bug」，属于明显混杂，应提示并询问是否拆分（拆分为 hunk 级，用 `git add -p`）。

## 常见拆分模式

| 现状 | 拆分结果 |
|------|----------|
| 新增功能 + 顺带改了 README | `feat(…): 新增…` 与 `docs: 补充…` 两条 |
| 修 A bug + 修 B bug（无关） | `fix(…): 修复 A` 与 `fix(…): 修复 B` 两条 |
| 重构 + 行为没变 | 单条 `refactor(…): …` |
| 加依赖 + 写代码 | `build(…): 引入 xx` 与 `feat(…): …` 两条 |

## 与 Conventional Commits 的关系

原子的「一件事」往往天然对应一个清晰的 `type(scope): 主题`。所以：**先想清楚这次改动能拆成几个「一件事」，再为每件事写一条 message**，反过来又被 message 的清晰度所检验。

## 直觉检验清单

提交前对每组自问：

- [ ] 这一组只做了一件事吗？
- [ ] 这条 message 一句话能说清这组改动吗？
- [ ] 单独 revert 掉它，项目仍能工作 / 语义仍成立吗？
- [ ] 组内没有混入无关的 feat / fix / docs 吗？
